# 团队容量与资源隔离验收（2026-10-22）

## 结论

已部署隔离配置并完成真实负载、Langfuse 短时故障恢复与原数据保全检查。建议现阶段先按 **5 个同时活跃的工作流**试运行，参考组合为 **2 个连续检索、2 个连续写作、1 个后台入库**。这不是注册人数限制，也不是任意组合的 5 人长期服务保证。

10 分钟连续发起工作、再等待在途操作完成，共 699/699 项成功；检索 P95 2.28 秒，写作 P95 32.34 秒。完整 17 页论文最终成功入库，但耗时 11 分 12 秒，超过预设 10 分钟目标。结论是检索、写作与短时追踪故障恢复通过，大文档吞吐仍有限，不能将本次结果写成全部性能目标通过。

## 范围与测量口径

实测机器 Mac16,10，10 核 CPU、16 GiB 内存；服务在 Colima 的 4 vCPU / 8 GiB Linux VM 内运行。另有 LegCoBrain 服务共用 VM，本次未停止或改动它们。平台与 Langfuse 继续仅绑定本机。

容量指正在执行操作的并发工作流，不是注册人数、登录人数或团队总人数。检索使用原有具身智能资料库的 6 份资料、220 个可读分块，768 维本地向量；写作使用真实 DeepSeek、8 个冻结检索片段，要求 600–900 字中文简报。短阶梯上传为公开 π0 论文的两页文本 PDF（约 1.9 MB）和约 2 KB 文本；持续负载还加入完整 17 页原论文（约 7.9 MB）。完成点是解析、分块、向量索引全部就绪，完整论文的耗时单列。

测试使用一个专用验收账号、独立上传库和 8 篇独立槽位稿件，没有模拟不同用户之间的权限竞争。上传库分块大小 2000、重叠 0；关闭摘要、OCR/视觉推理、图谱与问题生成，仅测文字解析和向量索引。压测稿不自动接受候选稿、不启用自动学习，不写入个人习惯；历史修订与学习闭环沿用[此前独立功能验收](RESEARCH_SEMANTIC_LANGFUSE_ACCEPTANCE_2026-10-22.md)，本次不把它们宣称为已完成并发容量验收。

评估目标：检索 P95 ≤ 5 秒，写作 P95 ≤ 120 秒，小文件入库 P95 ≤ 120 秒，完整论文单次目标 ≤ 600 秒；无业务错误、无新增 OOM/非计划重启；VM 可用内存至少 1 GiB。P95 使用 nearest-rank，并给出样本量。请求不由测试器自动重试；服务端异步任务可能重试。模型、索引和系统缓存未清空，不能称为严格冷启动测试。

## 已落实的隔离

- 前端 128 MiB / 0.5 CPU；应用 1 GiB / 1.5 CPU，Go 软内存目标 768 MiB；数据库 1 GiB / 1.5 CPU；解析服务 768 MiB / 0.75 CPU；业务 Redis 256 MiB / 0.5 CPU。
- 应用和数据库 CPU 竞争权重 2048；Langfuse worker/ClickHouse 与后台向量服务权重 256。CPU 权重仅在竞争时生效，不是专用物理核。
- Langfuse web、worker、ClickHouse 各最多 1 CPU；web 保持较高接收优先级。保留已有内存上限，避免压缩到不足以启动。
- 业务数据库连接池 20 个活动、5 个空闲；Langfuse 每个 Prisma 客户端连接池限制为 5。两者使用不同数据库和角色，但共享 PostgreSQL 进程，仍不是独立故障域。
- 核心入库、后台维护、附件 OCR 并发均为 1；解析 gRPC worker 为 2。入库先前并发 2 的四工作流测试出现 137 秒小文件等待，因此最终降低到 1，避免同一后台向量队列互相争抢。现有后台模型限流不限制同步研究写作，不能用模型配置的数字冒充已验证的用户并发上限。
- 实时查询与后台入库使用不同 Ollama 进程，分别最多 2 CPU / 2 GiB、1.5 CPU / 2 GiB；后台只读挂载同一份模型文件。按显式 background context 路由，后台不可用时由任务重试，不回退挤占查询服务。模型、向量维度和既有索引不变。

两个进程对同一输入输出的 768 维向量逐值一致，余弦相似度为 1；证据为 `embedding-consistency.json`。原有 220 个向量不需要重新构建。

以上是单服务上限与竞争优先级，不是内存预留承诺；各容器上限之和高于 VM 内存，因此必须同时看实测余量和队列，不能把这些配置理解为任意负载下都不会 OOM。

## Langfuse 上报修复

1. 原 OpenTelemetry 批处理默认 30 秒导出期限会截断 exporter 的 60 秒重试窗口。显式设置每次 HTTP 请求 10 秒、重试预算 60 秒、批次总期限 70 秒；保留官方重试实现与永久错误不重试的语义。
2. 批次 64、总 pending（含在途）上限 2048，应用路径非阻塞。新增 admitted、pending、OTLP accepted、queue dropped、terminal unconfirmed 等计数；OTLP 接收成功不能代替 Langfuse 实际落库验证。
3. Langfuse 4.67.0 worker 的 BullMQ 阻塞 Redis 连接不适用空闲 socket timeout。仅 worker 设置 `REDIS_SOCKET_TIMEOUT_MS=0`，保留 TCP keepalive/reconnect；web 不使用此例外。
4. 排查发现宿主环境 `LOG_FORMAT=json` 被 Compose 继承，而原生 logger 将其当字面模板，所有日志退化为单词 `json`。本地发行配置改用独立 `RESEARCH_LOG_FORMAT`，默认原生格式，恢复可用的上报诊断日志。先前 `errors-before.json` 的零计数因此不能证明没有错误。

缓冲仍是有界内存队列：长于重试窗口的故障、队列满、应用崩溃可能留下未确认记录；未实现持久化 outbox，不宣称零丢失。

## 实测结果

### 最终配置：连续混合负载

2026-10-22 17:50:49–18:02:02（北京时间），连续 600 秒发起操作，随后约 72 秒等待在途任务完成；没有超时或错误导致停止。5 个槽位固定执行检索、检索、写作、写作、上传。全窗口实际活跃工作流峰值 5、时间加权均值 4.52，均值包含最后仅剩论文入库的收尾时间。

| 操作 | 成功/次数 | P50 | P95 | 最慢 | 预设目标 |
| --- | ---: | ---: | ---: | ---: | --- |
| 原库语义检索 | 641/641 | 1.77 秒 | 2.28 秒 | 3.07 秒 | 通过，P95 ≤ 5 秒 |
| DeepSeek 生成研究候选稿 | 57/57 | 20.37 秒 | 32.34 秒 | 40.92 秒 | 通过，P95 ≤ 120 秒 |
| 完整 17 页 PDF 入库至索引就绪 | 1/1 | 单次 672.01 秒 | 样本不足 | 672.01 秒 | 未达标，单次目标 ≤ 600 秒 |

论文 7,942,659 字节、29 个已就绪向量分块、56,227 个分块字符。上传 HTTP 返回只用了约 0.10 秒，不把这个数字冒充入库耗时。其 knowledge ID 为 `79304e2d-c06c-4345-bbec-59a70d95fffb`。57 次候选稿累计输出 129,902 字符，含 Markdown 与引用，实际每篇平均约 2,279 字符；600–900 字是提示要求，不是精确的响应长度限制。

### 资源余量

`resources-steady.summary.json` 只统计最终连续负载窗口；335 个容器采样点、67 个宿主与 VM/队列采样点，无采样缺口。

| 指标 | 结果 |
| --- | --- |
| VM CPU（4 vCPU 总量为 100%） | 平均 90.4%，峰值 97.0% |
| VM 可用内存 | 最低 2.36 GiB，平均 2.54 GiB |
| 宿主 CPU（10 核总量为 100%） | 平均 45.8%，峰值 56.8% |
| VM Docker 磁盘可用空间 | 最低 8.38 GiB |
| 新增 OOM / 非计划重启 / 不健康采样 | 均为 0 |

主要压力来自两个 CPU 向量进程，VM CPU 已接近当前额度；内存仍有余量。宿主剩余 CPU 不会自动供给受限的 4 vCPU VM。团队增长前应优先处理索引算力与 VM 磁盘空间，再按真实资料量复测；不能仅增加上传并发。大批论文建议排队或错峰入库。

### Langfuse 真实中断与落库核对

仅暂停 Langfuse web 容器 40 秒，应用保持运行。暂停期间两次检索分别约 0.61、0.56 秒完成，一次真实写作约 21.01 秒完成。恢复后，3/3 条请求链路和 7/7 个最低必需观测节点均从 Langfuse API 读回，父子链路完整。测试进程以定时器和 finally 保证恢复服务。证据：`outage-verification.json`。

最终连续负载的 699/699 条请求链路、1456/1456 个必需节点全部落库；整个实验各阶段的 992/992 条链路、2083/2083 个必需节点全部落库。后者包含保留的早期测试器错误请求，不能据此声称整个实验的 992 次业务操作全部成功。后台批次和重试的精确总 span 分母未知，因此不称为全部 span 的精确送达率。

最终应用进程上报统计：4085 admitted、4085 OTLP accepted、pending 0、queue dropped 0、unconfirmed 0、failed batches 0，见 `delivery-final.json`。连续负载期间未检出 worker 的 socket timeout 或应用的导出失败特征。此次 40 秒中断通过，不代表长时间宕机、进程崩溃也能无损恢复。

`resources-stable.jsonl` 包含故意暂停引起的 Langfuse web 不健康采样；这些不应算作正常负载下的故障，也没有被从原始证据删除。正常连续负载使用单独的 `resources-steady.jsonl` 统计。
